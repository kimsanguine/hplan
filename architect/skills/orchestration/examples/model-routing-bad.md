# 나쁜 예제 — Model Routing (orchestration Router 패턴)

## 사용자 요청
"비용을 줄이려고 거의 모든 고객 질문을 T1 모델로 보내고 싶어. 만약 답변이 이상하면 사용자가 피드백 줄 테니까."

## 거절 이유
- 라우팅 규칙이 **과도하게 보수적** (T1 사용률 목표 >80%)
- 실제로는 많은 작업이 T1 능력 범위를 넘음 (복잡한 진단, 전략)
- 폴백 없이 T1 실패 시 사용자 경험 악화 → 신뢰도 하락
- 품질 목표(>90%)를 달성 불가능

## 올바른 Model Routing
- **Trigger Gate**: 작업 복잡도에 따라 T1/T2/T3 혼합 사용
- **Fallback 필수**: T1 실패 → T2 → T3 자동 재시도 (ModelResolver 폴백 체인)
- **Quality Gate**: 최종 출력이 >90% 품질 충족 확인 후만 반환 (2단계 품질 게이트)

## 수정 방향
"비용을 줄이면서도 품질을 유지하려면?" → 라우팅 규칙을 데이터 기반으로 수립
"T1 모델이 부족해 보이면?" → 폴백 전략으로 자동 상향 조정
"실제로는 어느 정도를 T1/T2/T3에 할당할 수 있을까?" → 파일럿 테스트로 라우팅 정확도 검증

## 추가 반사례 (프로덕션 안티패턴)

```
반사례 1: 무분별한 T1 라우팅
"거의 모든 작업을 T1로"
- 실제로는 많은 작업이 T1 능력 부족
- 품질 점수: 65% (목표 90% 미달)
- 폴백 발동 50% (비용 1.5배, 신뢰도 하락)

반사례 2: 라우팅 규칙이 애매함
"복잡도에 따라 선택" (정의 없음)
- 동일한 작업도 때마다 다른 모델로
- 예측 불가능, 비용 제어 불가
- → Config-driven 분류 규칙 + confidence_threshold로 결정론화

반사례 3: 폴백 없음
"T1으로 했는데 실패하면 그냥 오류"
- 안정성 문제
- 사용자 이탈
- → ModelResolver의 Primary → Fallback 1 → Fallback 2 체인 필수

반사례 4: 라우팅 비용이 절감보다 큼
"T1 선택 여부를 판단하는 라우터를 T3 모델로 실행"
- 라우터 비용: $0.015
- T1 절감: $0.001
- 순손실: $0.014/요청
- → Model Routing의 Boundary Check 위반 (라우팅 오버헤드 > 절감)
```
